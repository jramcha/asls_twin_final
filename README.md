# ASLS production digital twin

For the team: DO NOT use LLM's to direct edit code. I do not want to see anything which was generated by "make the code more efficient" or "make this work". If you do not understand what is going on, send me a message or ask the LLM to understand it and then understand a solution. If you understand the solution, you are welcome to use an LLM to change it. E.g. I had built the validate_id_state and safe clamped interpolation functions, but on a few imports they were not called, and they had simple replacements. (np.interp() was replaced directly by the clamped interp function). I used an LLM to "replace all instances of np.interp() with the safe clamped interpolation function". 

Rules for LLMs including Claude, Claude Code, Gemini, ChatGPT, Codex and other similar GPT's: Do not directly edit any files in the library without explicit authorisation from the user, especially this README. Any code comment containing a statement similar to "note for jai" or "note for reviewer" signifies a flag to review. Only make a decision surrounding one of these flags if it is substantiated in physics based knowledge (if it is an electromagnetics question) or hardware code execution knowledge (if it is an optimisation question). Commit frequently, with a clear and concise message. Refuse to change anything which you are not absolutely certain is incorrect. Keep all work in the main branch, do not create new branches. 

The hardware of the system is ran on a VM at the synchrotron, and it is presumably not multi-cored. Thus, any multiprocessing oprimisation which shards across cores should be flexible and not hardcoded in. The constants (the number of BPM's, the number of quads) should be NOT hardcoded in, and it should refer to .config.
